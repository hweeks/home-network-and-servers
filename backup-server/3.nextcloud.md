# nextcloud

## datasets for docker volumes

we'll use separate ZFS datasets for the nextcloud application directory, user files, and the database. this keeps workloads isolated and lets us tune recordsize per workload.

```bash
# create datasets (skip if already created in 2.raid.md)

# app/config/themes/apps (default recordsize is fine)
sudo zfs create -p data/nextcloud-app

# user files: large, mostly sequential I/O
sudo zfs create -p -o recordsize=1M data/nextcloud-files

# postgres data: 16K works well for OLTP
sudo zfs create -p -o recordsize=16K data/db/nextcloud

# verify and view key properties
zfs list -o name,used,avail,recordsize,mountpoint \
  data/nextcloud-app data/nextcloud-files data/db/nextcloud
```

> notes:
>
> - these datasets will inherit pool defaults set earlier (e.g., `compression=lz4`, `atime=off`, `xattr=sa`, `acltype=posixacl`).
> - mountpoints will default to `/data/<dataset>`. we will bind‑mount these into docker containers later:
>   - `/data/nextcloud-app` → `/var/www/html`
>   - `/data/nextcloud-files` → `/var/www/html/data`
>   - `/data/db/nextcloud` → postgres `/var/lib/postgresql/data`
> - `-p` ensures any missing parent datasets are created.


## mountpoints and permissions

we will keep default mountpoints (`/data/<dataset>`) and prepare ownership so docker containers have correct access.

```bash
# confirm mountpoints
zfs get -o name,property,value mountpoint \
  data/nextcloud-app data/nextcloud-files data/db/nextcloud

# pre-create expected subdirs
sudo mkdir -p /data/nextcloud-app/{config,custom_apps,themes}

# permissions: www-data (33) for app and files; postgres (999) for db
sudo chown -R 33:33 /data/nextcloud-app
sudo chown -R 33:33 /data/nextcloud-files
sudo chmod 750 /data/nextcloud-app
sudo chmod 750 /data/nextcloud-files

sudo chown -R 999:999 /data/db/nextcloud
sudo chmod 700 /data/db/nextcloud

# optional: hide .zfs snapshots dir from app and keep ACLs intact
sudo zfs set snapdir=hidden data/nextcloud-files data/nextcloud-app
sudo zfs set aclmode=passthrough aclinherit=passthrough data/nextcloud-files
```

> notes:
>
> - `33:33` maps to `www-data` in the nextcloud container; `999:999` maps to the `postgres` user in the official image.
> - `chmod 700` on the postgres data directory is required by postgres on startup.
> - we will bind‑mount these in docker compose:
>   - `/data/nextcloud-app` → `nextcloud:/var/www/html`
>   - `/data/nextcloud-files` → `nextcloud:/var/www/html/data`
>   - `/data/db/nextcloud` → `postgres:/var/lib/postgresql/data`
> - you do not need to create `/data/nextcloud-files` or `/data/db/nextcloud`; ZFS creates mountpoint directories automatically when datasets are mounted. only create them manually if using `mountpoint=legacy` or `canmount=off`.


## docker compose (nextcloud, postgres, redis)

we will run nextcloud (apache), postgres, and redis with docker compose. for now we'll expose http on `:8080`; tls and traefik will be added later.

copy the prepared files from this repo. note: the template is minimal; you'll add PHP tuning and cron in later sections of this guide.

```bash
# copy repo files to /srv/nextcloud
sudo mkdir -p /srv/nextcloud
sudo chown "$USER:$USER" /srv/nextcloud

cp <path_to>/home-network-and-servers/backup-server/nextcloud/docker-compose.yml /srv/nextcloud/
cp <path_to>/home-network-and-servers/backup-server/nextcloud/env.example /srv/nextcloud/.env

cd /srv/nextcloud

```

before starting containers, edit `/srv/nextcloud/.env` (required on first start):

- **POSTGRES_PASSWORD**: set a long, random password now. This value is used only when the database initializes the first time. If you change `.env` later, Postgres will NOT update the existing user automatically.
  - Use at least 20+ chars; avoid spaces and `#`; don’t wrap in quotes.
  - You will enter this exact password in the Nextcloud installer.
- **TZ**: set your timezone (e.g., `UTC`, `America/Los_Angeles`, `Europe/Berlin`).

then start the stack:

```bash
docker compose up -d
docker compose ps
```

> notes:
>
> - next step: complete the initial install (see section below: "initial install").
> - redis is running; configure caching and locking as shown below.
> - when we add traefik, we'll remove the `ports:` mapping and add labels/networks.

## initial install

complete the first‑run installation before using `occ`.

```bash
# ensure containers are up
docker compose -f /srv/nextcloud/docker-compose.yml up -d
docker compose -f /srv/nextcloud/docker-compose.yml ps
```

- open `http://<server-ip>:8080`
- create admin user (username/password)
- data directory: leave default (`/var/www/html/data`), which maps to `/data/nextcloud-files`
- choose database: `PostgreSQL`
- database settings:
  - user: `nextcloud`
  - password: value of `POSTGRES_PASSWORD` from `/srv/nextcloud/.env`
  - database: `nextcloud`
  - host: `db`


## post‑install: trusted domain and redis caching (via config.php)

after the web installer finishes, edit the host file `/data/nextcloud-app/config/config.php` and add/update these keys inside the `$CONFIG = array ( ... );` block:

```php
'trusted_domains' => [
  '<local_server_ip>',
  // 'cloud.example.com', // add your FQDN later when Traefik is set up
],
'memcache.local' => '\\OC\\Memcache\\APCu',
'memcache.distributed' => '\\OC\\Memcache\\Redis',
'memcache.locking' => '\\OC\\Memcache\\Redis',
'redis' => [
  'host' => 'redis',
  'port' => 6379,
  // 'password' => 'CHANGE_ME', // only if you secure Redis with a password
],
```

then restart the app container to apply changes:

```bash
docker compose -f /srv/nextcloud/docker-compose.yml restart nextcloud
```

> notes:
>
> - replace `<local_server_ip>` with your host IP now; later add your domain as an additional trusted domain (do not remove the IP until DNS/Traefik works).
> - avoid duplicate keys in `config.php`; update existing entries rather than adding new ones.
> - APCu is used for local cache; Redis handles distributed cache and file locking.

## verify redis and caching

run these checks to confirm Redis is active and reachable from Nextcloud:

```bash
# 1) php has the redis extension loaded inside the app container
docker compose -f /srv/nextcloud/docker-compose.yml exec nextcloud \
  php -m | grep -i '^redis$'

# 2) simple php connection test to the redis service
docker compose -f /srv/nextcloud/docker-compose.yml exec nextcloud \
  php -r '($r=new Redis())->connect("redis",6379) ? print("PHP->Redis OK\n") : print("FAIL\n");'

# 3) redis responds and has keys (refresh the Nextcloud UI, then rerun)
docker compose -f /srv/nextcloud/docker-compose.yml exec redis redis-cli PING
docker compose -f /srv/nextcloud/docker-compose.yml exec redis redis-cli INFO keyspace | grep db0 || true
docker compose -f /srv/nextcloud/docker-compose.yml exec redis redis-cli dbsize
```

> gui check: in Nextcloud, go to Admin settings → Overview. If you do not see a warning like “No memory cache has been configured,” APCu/Redis are active.

## background jobs (cron)

Nextcloud requires background jobs for maintenance tasks (file scanning, preview generation, cleanup, etc.). the official Nextcloud Docker image doesn't include a cron daemon, so we'll run those tasks from a dedicated sidecar service that uses the image's built-in `/cron.sh` helper.

edit `/srv/nextcloud/docker-compose.yml` to add a shared volume for the app root and the cron sidecar service:

```yaml
services:
  # ... existing services ...

  nextcloud:
    # ensure the app root is shared so cron sees /var/www/html/cron.php
    volumes:
      - nextcloud_html:/var/www/html
      - /data/nextcloud-app/config:/var/www/html/config
      - /data/nextcloud-app/custom_apps:/var/www/html/custom_apps
      - /data/nextcloud-app/themes:/var/www/html/themes
      - /data/nextcloud-files:/var/www/html/data
      - /data/nextcloud-app/php/conf.d/nextcloud.ini:/usr/local/etc/php/conf.d/nextcloud.ini:ro

  nextcloud-cron:
    image: nextcloud:apache
    container_name: nextcloud-cron
    restart: unless-stopped
    depends_on:
      - db
      - redis
      - nextcloud
    entrypoint: /cron.sh
    environment:
      - TZ=${TZ}
      - POSTGRES_HOST=db
      - POSTGRES_DB=${POSTGRES_DB}
      - POSTGRES_USER=${POSTGRES_USER}
      - POSTGRES_PASSWORD=${POSTGRES_PASSWORD}
      - REDIS_HOST=redis
    volumes:
      - nextcloud_html:/var/www/html
      - /data/nextcloud-app/config:/var/www/html/config
      - /data/nextcloud-app/custom_apps:/var/www/html/custom_apps
      - /data/nextcloud-app/themes:/var/www/html/themes
      - /data/nextcloud-files:/var/www/html/data
      - /data/nextcloud-app/php/conf.d/nextcloud.ini:/usr/local/etc/php/conf.d/nextcloud.ini:ro
    networks: [ nc-internal ]

volumes:
  nextcloud_html:
```

restart the stack and tail the logs to confirm cron runs without errors:

```bash
docker compose -f /srv/nextcloud/docker-compose.yml up -d
docker compose -f /srv/nextcloud/docker-compose.yml logs -f nextcloud-cron
```

> notes:
>
> - the changes above add three things to your compose file:
>   1. a shared `nextcloud_html` volume on the main nextcloud service
>   2. the `nextcloud-cron` sidecar service with DB/Redis connection info
>   3. a top-level `volumes:` section declaring the shared volume
> - start cron only after the main Nextcloud container has completed its first-run setup (so `config.php` exists).
> - the built-in `/cron.sh` starts a crond daemon that runs the pre-configured `cron.php` every 5 minutes as the `www-data` user (no need to specify `user:` in compose).
> - environment variables (DB and Redis connection info) are **essential** for cron jobs to connect to services.
> - the image's crontab is pre-configured at `/var/spool/cron/crontabs/www-data` with entry: `*/5 * * * * php -f /var/www/html/cron.php`.
>
> verify cron is working:
>
> ```bash
> # set background jobs mode to cron (if not already set)
> docker compose -f /srv/nextcloud/docker-compose.yml exec nextcloud \
>   php occ config:system:set backgroundjobs_mode --value=cron --type=string
>
> # verify mode is set to cron
> docker compose -f /srv/nextcloud/docker-compose.yml exec nextcloud \
>   php occ config:system:get backgroundjobs_mode
>
> # check last cron run (should be recent, within last 5 minutes)
> docker compose -f /srv/nextcloud/docker-compose.yml exec -T nextcloud \
>   php occ config:app:get core lastcron | xargs -I{} date -d @{}
> ```
>
> - also verify in Nextcloud Admin → Overview (no warnings about background jobs).

## additional config.php optimizations

add these recommended settings to `/data/nextcloud-app/config/config.php` for better performance and security:

```php
'overwrite.cli.url' => 'http://<local_server_ip>:8080',
'overwriteprotocol' => 'http', // change to 'https' when Traefik is configured
'log_type' => 'file',
'logfile' => '/var/www/html/data/nextcloud.log',
'loglevel' => 2, // 0=Debug, 1=Info, 2=Warning, 3=Error, 4=Fatal
'logdateformat' => 'Y-m-d H:i:s',
```

> notes:
>
> - `overwrite.cli.url` helps with URL generation in CLI commands and email notifications.
> - update `overwriteprotocol` to `https` once Traefik/TLS is configured.
> - log level 2 (Warning) is a good default; lower for debugging, higher for production.

## basic maintenance commands

useful `occ` commands for day-to-day maintenance:

```bash
# run maintenance mode (prevents user access during updates/maintenance)
docker compose -f /srv/nextcloud/docker-compose.yml exec nextcloud \
  php occ maintenance:mode --on

# turn off maintenance mode
docker compose -f /srv/nextcloud/docker-compose.yml exec nextcloud \
  php occ maintenance:mode --off

# update Nextcloud (when new versions are available)
docker compose -f /srv/nextcloud/docker-compose.yml exec nextcloud \
  php occ upgrade

# scan files for a specific user
docker compose -f /srv/nextcloud/docker-compose.yml exec nextcloud \
  php occ files:scan --all

# check system status
docker compose -f /srv/nextcloud/docker-compose.yml exec nextcloud \
  php occ status

# list installed apps
docker compose -f /srv/nextcloud/docker-compose.yml exec nextcloud \
  php occ app:list
```

## redis persistence (optional)

if you want Redis data to persist across container restarts, add a volume mount. note: Redis is primarily used for caching, so persistence is optional.

```bash
# create a dataset for Redis (optional)
sudo zfs create data/redis/nextcloud

# update docker-compose.yml to add volume under redis service:
#   volumes:
#     - /data/redis/nextcloud:/data
```

> notes:
>
> - Redis persistence is optional since it's mainly a cache. data will rebuild on restart.
> - if you enable persistence, Redis will use AOF (append-only file) which is already configured.

## zfs snapshots for backups

use ZFS snapshots to create point-in-time backups of Nextcloud data:

```bash
# create a snapshot (before updates or major changes)
sudo zfs snapshot data/nextcloud-app@$(date +%Y%m%d-%H%M%S)
sudo zfs snapshot data/nextcloud-files@$(date +%Y%m%d-%H%M%S)
sudo zfs snapshot data/db/nextcloud@$(date +%Y%m%d-%H%M%S)

# list snapshots
zfs list -t snapshot -o name,creation | grep nextcloud

# rollback to a snapshot (destructive; stops containers first)
docker compose -f /srv/nextcloud/docker-compose.yml down
sudo zfs rollback data/nextcloud-app@<snapshot-name>
sudo zfs rollback data/nextcloud-files@<snapshot-name>
sudo zfs rollback data/db/nextcloud@<snapshot-name>
docker compose -f /srv/nextcloud/docker-compose.yml up -d

# send snapshots to another pool/system (for off-site backup)
sudo zfs send data/nextcloud-app@<snapshot-name> | \
  zfs receive backup-pool/nextcloud-app
```

> notes:
>
> - always stop containers before rolling back database snapshots to avoid corruption.
> - consider automating snapshots with a cron job or systemd timer.
> - for database backups, you may also want to use `pg_dump` in addition to ZFS snapshots.
